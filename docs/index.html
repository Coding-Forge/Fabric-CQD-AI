CQD Analytics POC

Teams call quality data from Microsoft Graph, landed in Azure Data Lake and Microsoft Fabric, reported through a Direct Lake semantic model, and explored with an AI chat app. Built for Microsoft 365 GCC High and Azure Government.

Proof of concept. This is prepared code and a working demonstration, not a deployed or customer-accepted solution. The quality classification thresholds are illustrative and are not verified CQD reporting equivalence.

Overview

Call Quality Dashboard (CQD) data is not directly exportable in a form that fits a modern analytics stack. This POC pulls call records from the Microsoft Graph callRecords API, keeps every version as an immutable raw snapshot, flattens them into curated tables, and serves them to a Power BI report and a natural-language chat page.

  • Source: Microsoft 365 GCC High through Graph (graph.microsoft.us), read-only, application permission CallRecords.Read.All.
  • Storage: ADLS Gen2 Bronze, then Fabric Lakehouse Delta tables (Silver and Gold).
  • Reporting: Direct Lake semantic model with a two-page report.
  • AI: Azure OpenAI answers questions by running read-only SQL over the curated tables.

Users are pseudonymized with a salted hash before they reach Silver, so names, UPNs and IP addresses are not exposed to reports or to the model.

Pipeline

A Fabric pipeline runs two notebooks in sequence on an hourly schedule:

  1. Ingest (notebooks/cqd_ingest_graph_to_bronze.ipynb): reads the service principal secret from Azure Key Vault, pulls call records for a 24-hour lookback, and writes new versions to Bronze. Versions already in the ledger are skipped.
  2. Transform (notebooks/cqd_bronze_to_silver_gold.ipynb): flattens Bronze into Silver, replacing child tables per call and merging silver_calls last so a failed run self-repairs, then rebuilds Gold.

An end-to-end run takes about eight minutes, mostly Spark startup. The Key Vault secret is fetched through the vault REST API because notebookutils rejects Azure Government vault hosts.

Report

A Direct Lake semantic model reads the Silver and Gold tables in place, with no import copy. The report has two pages covering call volume, sessions, participants, and per-stream jitter, round-trip time and packet loss. A local Power BI Project in PBIP-Local/ provides the same model over exported sample CSVs for offline exploration.

Chat app

chat/ is a local page where users ask questions in plain language. It reads only the Silver and Gold tables, never Bronze files.

  1. Lists the silver_* and gold_* tables through the OneLake API.
  2. Replays each Delta _delta_log to find the active parquet files and loads them into in-memory SQLite.
  3. Azure OpenAI answers by calling a read-only run_sql tool. Only SELECT is allowed, rows are capped at 200, and the server binds to localhost.

Source and confidence score

Every answer shows the SQL that ran, the parquet files read, and a score from 0 to 100:

ComponentWeightMeaning
Query success25%Queries ran without error and returned rows, and were not truncated.
Answer grounded in results45%Share of numbers in the answer that appear in the query results.
Source completeness30%Tables read, scaled by how many streams actually reported metrics.

Bands are High (80 or more), Medium (50 to 79) and Low (below 50). The score is capped at 20 when no query returned rows. It is a heuristic, not a measured accuracy.

Setup

Nothing environment-specific is stored in the repository. Set these in your shell profile:

export FABRIC_TENANT_ID=<tenant-id>
export FABRIC_CLIENT_ID=<service-principal-client-id>
export FABRIC_CLIENT_SECRET=<from a secret store>
export ONELAKE_HOST=<onelake-dfs-host>
export FABRIC_WORKSPACE=<workspace>
export FABRIC_LAKEHOUSE=<lakehouse>
export AZURE_OPENAI_ENDPOINT=<endpoint>
export AZURE_OPENAI_API_KEY=<key>
export CQD_STORAGE_ACCOUNT=<storage-account>   # cqd.ingest only
python -m venv .venv && .venv/bin/pip install -r requirements.txt -r chat/requirements.txt
.venv/bin/python -m chat.server --check   # reads the tables only; no model needed
CHAT_PORT=8001 .venv/bin/python -m chat.server

The Fabric notebooks run in the cloud and cannot read your shell profile. Set their parameters (TENANT_ID, CLIENT_ID, STORAGE_ACCOUNT, KEY_VAULT_URL, SECRET_NAME) in your Fabric copy; the committed notebook contains placeholders and stops if they are not replaced.

Run the tests with .venv/bin/python -m unittest tests.test_chat tests.test_graph tests.test_probe tests.test_storage tests.test_functions.

Security

  • Secrets live in Azure Key Vault or environment variables, never in source or notebooks.
  • Raw call data and generated samples are Git-ignored.
  • Identifiers such as tenant, client, storage and vault names are placeholders in the repository.
  • Users are hashed before reaching Silver, Gold, the report or the model.
  • The chat SQL guard allows only SELECT/WITH, forbids write keywords, and runs with PRAGMA query_only=ON.
  • Grant the service principal only the roles it needs: Graph CallRecords.Read.All, workspace access, and Key Vault secret read.

Status and limits

  • Verified end to end on a small sample: 5 calls, 10 sessions and 60 media streams, matching between the pipeline, report and chat.
  • About 62% of streams report quality metrics; the rest are NULL because Teams did not report them.
  • Not yet tested: scale and Graph throttling at 100K+ records per day, and an unattended scheduled run after secret rotation.
  • The chat reads tables into memory, which suits a POC but not large volumes.
